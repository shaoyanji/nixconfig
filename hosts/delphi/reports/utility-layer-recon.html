The utility layer: seven candidates, checked against reality

A verification-first pass over the proposed small-model layer — shell ghost text, offline wiki lookup, tool routing — against eisen’s 8 GB RX 5700, poseidon’s 4 GB RTX 3050 Ti, and delphi’s 2 OCPU ARM instance.

verified on Hugging Face + GitHub 7/7 candidates resolve 2 are not what the brief assumed 1 model is six days old and off-list

Executive summary

Every candidate on the list exists. That is worth saying plainly, because the brief expected the opposite: small-model names churn, and several of these are one-person uploads with double-digit likes. All seven resolved to a real repository with real weights, a real license and a real quant or runtime. None were hallucinations.

Three findings change the build:

  1. Needle 2 is not a GGUF and not a chat model. It is a 45M-parameter tool-calling engine — a 14 MB binary, 28 MB session RAM — that emits grammar-constrained JSON and carries a calibrated confidence head. It cannot be dropped into llama-server, and it should not be asked to write prose. As a router for a wiki agent it is the best thing on this list by a wide margin; as an autocomplete model it is useless.
  2. The strongest candidate is not on the list. LiquidAI/LFM3-1.7B shipped 2026-10-23 — six days ago. 1.73B, 256K context, ~1 GB at 4-bit, official GGUF, and post-trained specifically for agentic harnesses “such as Hermes Agent, Pi, and OpenClaw” — which is this fleet’s actual stack. Its family also ships vision, audio, omni and decision variants, which is the decision-model thread from the earlier discussion. The catch is the license: LFM Open License v1.0, not Apache-2.0.
  3. Nothing in this layer may compete for eisen’s VRAM. Strata already holds roughly 6.1 GB of the 8 GB card while the main model is resident. Any utility model on eisen has to be CPU-pinned or you are choosing it over the model you use. That constrains the build order more than model quality does.

And one finding that changes the shape of the project rather than the model list: the autocomplete integration named in the brief does not apply here. pi-shell-autocomplete is a Pi-TUI package; there is no pi binary on any host, and the editor is nixvim. The model side of ghost text is ready; the harness is unwritten. That makes the router the only deployable first step, not merely the cheapest.

Five details in the prompt do not match the registry or the model cards. They matter because two of them decide which backend is even available.

The 35B-A3B class is the chat tier. Decision models are cheap enough to fine-tune in an hour and are scored with accuracy, not taste.

What each caveat actually means

  • kitty-bash-llm is a single-person fine-tune of a 0.5B base: 5 likes, 941 downloads, no published evaluation, and the README makes capability claims without numbers. Its GGUF is real and llama.cpp will load it. Treat it as “worth 379 MiB of disk to try”, not as a shell specialist with evidence.
  • ShellWhisperer-1.5B is tagged uncensored and has no benchmark section. The license field is genuinely ambiguous: the base repo says Apache-2.0, two MLX derivatives say MIT. For personal fleet use that is inert; for anything shipped, read the LICENSE file rather than the tag.
  • NGARi-tool is a LoRA adapter that has also been merged and quantised — unlike Kev-4B, it needs no special build. It ships its own evaluation JSON, which is more than the other two hobby projects do, but 109 downloads means no third-party signal exists.
  • Needle 2 is the one genuine architecture on the list: a Simple Attention Network with a Hadamard MLP instead of an FFN, compressed to CQ2-bit, with a byte-level grammar compiled from your declared tool schemas. The consequence cuts both ways — it cannot free-form, and that is the point.
  • LFM3-1.7B is the only model here whose card states an intended harness that this fleet runs. It also states its limits: “not recommended for agentic coding or complex multi-step reasoning due to its small size.”
  • pi-shell-autocomplete is a Pi package, not a general terminal plugin. It requires the Pi TUI, zsh with compinit, and node-llama-cpp. On a bash/tmux/nushell fleet it does nothing until Pi is the editor.

The number that governs everything: 6.1 GiB

When eisen yields to a game, the guard frees “the resident expert arena plus the 6.1 GiB of VRAM”. That is the utility layer’s entire headroom on that host, and it is already spoken for by the thing you actually use. A 3B utility model on the card means choosing it over the 125B, mid-session, which is exactly the failure the brief asked to avoid.

VRAM coexistence plan

Rank order, cheapest to most disruptive. The rule: the utility layer lives in RAM on eisen, and in VRAM only on poseidon, which has no main model to protect.

TierWhateisenposeidondelphi
A Needle 2 router Runs alongside Strata with no negotiation: 28 MB resident RAM, zero VRAM Same Native — the linux-arm64 binary
B CPU autocomplete server (1.5–1.7B, -ngl 0) Pin to 4 threads, --parallel 2, 2k ctx. Costs ~1.2 GB RAM and 1/3 of a core pair; never touches VRAM Optional fallback; better to use the GPU Viable but competes with the build budget — do not run during a rebuild
C GPU autocomplete (3B, -ngl 99) do not — evicts Strata or OOMs yes — 1.8 GiB of 4, leaves ~1.3 GiB for KV No GPU
D Second llama-server under llama-swap llama-swap is dormant since 2026-10-21 (superseded by Strata on :8085). Re-enabling it to host a utility model reintroduces the swap semantics you just retired Fine — own port, own unit Fine, but two models on 2 OCPU is a build-budget decision

Practical consequence for eisen: the utility server is a new standalone unit (own port, --ngl 0, MemoryMax), not a llama-swap child. Putting it under llama-swap would make it a sibling of the model you deliberately moved off llama-swap. 

# eisen: utility server, CPU-pinned, never a swap candidate
llama-server \
  --model /mnt/storage/models/LFM3-1.7B-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8092 \
  --threads 4 --threads-batch 8 \
  -ngl 0 --no-kv-offload \
  --ctx-size 4096 --parallel 2 \
  --jinja --metrics

Build order

Ordered by value per unit of risk, not by model quality. Each step is independently useful and none of them touches the main model.

1 · Needle 2 as the wiki/tool router measured: suggester

14 MB binary, 28 MB RAM, ARM64 build, grammar-compiled from your own JSON schemas, and a calibrated confidence head you can threshold. It answers exactly one question — “is this a lookup, which tool, what argument” — which is the whole decision the archivist needs before retrieval begins. It runs on delphi, which has no GPU and is always on. Nothing else on the list can be deployed there without cost.

Measured after deployment: 53 % tool agreement on Needle 3 (60 % on Needle 2), 99 % schema validity, and it withholds 70 % of calls — see Needle 3, measured. It ships as a CLI (needle-route), the only mode that measured cleanly.

2 · Ghost text — model first, harness second blocked on harness

The model side is settled: LFM3-1.7B (≈1 GB, CPU-pinned -ngl 0), with kitty-bash 0.5B as a 379 MiB latency probe to establish the floor. What is not settled is the insertion point, because Pi is not installed on this fleet and pi-shell-autocomplete therefore has no host to run on. Two real options:

  • nixvim inline completion — Neovim’s LSP inline-completion handler pointed at a tiny sidecar that speaks textDocument/inlineCompletion and forwards to the CPU-pinned server. This is the only path that reaches the editor you actually use daily; it is ~100 lines of glue that does not exist yet.
  • zsh ZLE widget — a model-backed ghost text beside the existing history-based zsh-autosuggestions. Cheap to write, but the two compete for the same region to the right of the cursor, so one has to yield.

Consequence for ordering: if ghost text waits on glue, do step 1 (the router) first — it is deployable today and needs no harness. That is a scope change from the brief, and it is the correct one.

3 · GPU ghost text on poseidon (Qwen2.5-Coder-3B, Q4_K_M)

The same model pi-shell-autocomplete recommends. On a 4 GB laptop card it is fully resident, and this is the only host where the utility layer gets real VRAM without a negotiation.

4 · Decision model, once there are labels

Not part of this recon, but the natural successor: LFM3 ships a decision variant, and Kev-4B proves the /v1/systemone shape works in llama.cpp. The gating fact is not the model, it is that you need 2–5k labelled decisions to score against.

The decisive experiment: fewer labels, not more

If the failure is label confusion, a 5-way router (graph / docs / inventory / world / none, no free-form argument) should beat a 6-way one. It does not:

RouterLabelsMatchActsDominant error
tool router653 %30 %repo ↔ wiki
plane router530 %4 %inventory → world, 8 of 10

“What gpu does eisen have” is tagged world knowledge. The model does not know that a hostname is a local object, and no amount of label reduction fixes that — it is a vocabulary problem at 2.1 bits, not a decision problem. So the router idea does not fail on its interface; it fails on the model.

The router already exists, deterministically — and it was broken

scripts/task/kg-ask.sh is a three-step router: keyword rules → a bundle (the question names a node, so return everything connected to it) → UNKNOWN with a menu. Its header records the measurements that removed a model from this path on 2026-10-19: rules 14/14 at 0 ms, paraphrase 6/10 → 10/10 with the bundle, unnamed 4/9 versus a Jev model’s 7/9 whose two misses were confidently wrong rather than visibly declined.

That is the same conclusion this page reached from the other direction, arrived at five weeks earlier and with better evidence. The reason the BEAM went unused is not that it is slow (28 ms on the socket versus 476 ms via jq) and not that a model should replace it: it is that task ops:ask was throwing kg-graph: REPO is not set and exiting 1. Every agent that tried the documented entry point got an error and reached for grep instead. kg-graph.sh now derives REPO from its own location, so the nine callers cannot forget it again.

Verdict

Keep qmd and the Elixir sidecar as the data plane. Route with the deterministic rules, and put Needle where its grammar is the whole value — extraction, classification, and constrained argument filling — not semantics. A 121M model at 2.1 bits cannot decide which subsystem owns a question about a fleet it has never seen; a 14-line keyword table can.

Integration sketches

pi-shell-autocomplete, preferring one model reference only

Kept for reference, not as a plan: this requires the Pi TUI, which this fleet does not run. If Pi ever becomes the editor, the extension reads a priority list of GGUF paths and takes the first that exists, so “configuring a model” is placing the file and ordering the list. 

// in the Pi extension config
ai: {
  enabled: true,
  modelPriority: [
    "~/.pi/agent/models/LFM3-1.7B-Q4_K_M.gguf",          // preferred
    "~/.pi/agent/models/qwen2.5-coder-3b-instruct-Q4_K_M.gguf",
    "~/.pi/agent/models/kitty-bash-llm-q4_k_m.gguf",     // latency floor
  ],
  debounceMs: 400,
  maxTokens: 40,
  contextSize: 2048,
  fileContext:     { enabled: true, maxFiles: 20 },   // disable on NFS/`/Volumes` paths
  historyContext:  { enabled: true, maxEntries: 10, historyPath: "~/.zsh_history" },
}

Model loading happens lazily on first ! input, so the first completion after a restart may stall. Ghost text silently disables if no model file is found — a missing model looks like “AI is off”, not an error.

A wiki agent that decides before it searches

Two halves: a router that emits a constrained call, and a retrieval backend. The router sees only schemas, never the corpus. 

tools = [{
  "name": "wiki_search",
  "description": "Full-text search the offline Kiwix corpus (BM25). Use for factual or encyclopedic questions.",
  "parameters": {
    "type": "object",
    "properties": {
      "query":   {"type": "string",  "description": "keywords, not a sentence", "minLength": 2, "maxLength": 80},
      "corpus":  {"type": "string",  "enum": ["wikipedia_en", "wikipedia_de", "wiktionary"]},
      "limit":   {"type": "integer", "minimum": 1, "maximum": 10, "default": 5}
    },
    "required": ["query", "corpus"]
  }
}, {
  "name": "repo_search",
  "description": "Search this repository's docs and notes (qmd BM25) for fleet-specific facts.",
  "parameters": {
    "type": "object",
    "properties": {
      "query":    {"type": "string", "minLength": 2, "maxLength": 120},
      "collection": {"type": "string", "enum": ["nixconfig", "vault", "skills"]}
    },
    "required": ["query", "collection"]
  }
}]

Backends already exist and should not be rewritten: wikisearch (Kiwix BM25 on frieren) and qmd search -c nixconfig. The loop is: route → execute → feed the top-k snippets back → answer with the retrieved record. The confidence head is what makes it safe: below threshold, answer “I don’t know” instead of guessing, which is the failure mode a 1.7B cannot self-detect. 

# shape of the loop, backend-agnostic
route   = needle.complete(question)          # {"type":"call","function_calls":[...],"confidence":0.87}
if route["confidence"] < 0.6: return refuse(question)
hits    = run(route["function_calls"][0])    # kiwix / qmd
answer  = model.complete(question, context=hits[:5])   # the *big* model, or none at all

Where the utility model deserves to write prose (it mostly doesn’t)

Keep the 1.7B on the classification and transformation side of the line: pick a tool, normalise a query, extract fields, decide whether a question needs retrieval at all. Any answer synthesis that cites sources should be done by the model that can hold the context — the main model — or by the retrieval layer itself.

Older-generation small models: where 0.5–3B is genuinely enough

The Qwen2.5-era weights (2024–25) are still the backbone of most of this list, and the honest answer is that the harness decides whether they work, more than the weights do. Concretely:

TaskVerdict at 0.5–3BWhy
Inline shell ghost text / FIM sufficient Short output (≤40 tokens), a strong local prior (directory listing + history), and a wrong suggestion costs one keystroke. This is the best-matched task on the list.
Fixed-label classification / routing sufficient 3–12 labels, grammar-constrained to the label set, scored by accuracy. Model size stops mattering once the output space is closed.
Structured extraction into a schema sufficient with a grammar Needle’s whole thesis: a 45M model with a byte-level grammar compiled from the schema beats a 3B free-forming JSON. Without the grammar, both fail.
Choosing 1 of ~12 tools borderline Works when descriptions are distinctive. Degrades fast past ~12; the fix is a retrieval head (Needle ships one), not a bigger model.
Multi-step tool use (2+ dependent calls) falls down Error compounding: each step at 90% is 81% over two, 66% over four. LFM3’s own card disclaims complex multi-step reasoning outright.
World knowledge / “what is X” falls down Not a size problem to solve with training: retrieve instead. Which is why the router matters and the corpus lives in an index.
Long context (>8k) summarisation falls down Effective attention collapses well before the advertised window; 2k ctx at 40 tokens is the honest operating point for ghost text.
Non-English (German) varies wildly Qwen2.5-era small models are English-first; LFM3 lists German among 16 languages, which is a genuine reason to prefer it for the German side of the portfolio.

One rule worth keeping: at this size, the constraint layer carries the quality. A 45M model with a compiled grammar and a confidence gate is more trustworthy than a 3B model asked to produce JSON politely, because the small one cannot emit an invalid call. That is also why the honest comparison on Needle’s card — trading wins with models 5–70× larger — is not marketing hype but a statement about how much of tool-calling is schema adherence rather than reasoning.

Open questions

  • ROCm or Vulkan on eisen? Two files in the repo disagree (see corrections). Until one wins, any candidate that is CUDA-only or ROCm-only is unresolvable, and the Strata unit’s own description may be aspirational.
  • Does Strata release VRAM on demand? The guard stops it on game start. If there is no idle-release, tier C on eisen is permanently impossible and the CPU plan is not a preference but a constraint.
  • Which ghost-text harness, now that Pi is out? Resolved that Pi is not installed (see corrections); open is whether the first integration is nixvim inline completion over a sidecar, or a zsh ZLE widget. The models do not change either way, and the router does not wait on it.
  • LFM Open License v1.0 terms. Permissive-looking but not Apache: read LICENSE before anything hosted or redistributed. Fine for local fleet use; the question is the capsule and any public endpoint.
  • Needle’s calibration in this domain. The confidence head is trained generally; the threshold that makes “refuse below 0.6” safe has to be measured on real fleet questions, not assumed.
  • Does kitty-bash-llm actually beat its base? It is a 0.5B fine-tune with no evaluation. A 30-question shell-completion probe against Qwen2.5-Coder-0.5B-Instruct would settle it in ten minutes.
