A workbench for editing token streams. Byte-anchored constraints, six reactors over the diff, and a wire that sends the tokens an edit changed — never the whole document.

Token Loom is a client and a server that edit text as tokens. A page sends token-level operations over a binary WebSocket; the server keeps the stream in a chunked piece table, re-tokenizes only the window an edit disturbed, runs six reactors over what changed, and streams back a minimal token diff plus warnings whose lifecycle does not flicker.

Why it exists

Every editing surface that shows tokens as chips eventually lies about them. Three failures show up over and over, and all three come from re-tokenizing the document on every keystroke:

  • The page disagrees with the server. A merge inside a word ripples past the visible window, so a full re-tokenization moves tokens the client thought were stable.
  • A constraint drifts off its text. "Token 40" means a different piece of text the moment anything before it is inserted, so a rule planted on a span starts describing a neighbour.
  • Warnings flicker. A rule broken, restored and broken inside a second produces three identities for one condition, and a feed nobody can read.

Token Loom is the smallest thing that avoids all three and stays fast enough to type into: bounded ripple instead of full re-tokenization, byte anchors instead of token indices, one stable identity per warning, and a diff small enough to send on every edit.

How it works

Rope

A chunked piece table of token runs, at most 256 tokens each. An edit splits the chunks it straddles, applies the change in one working buffer, and re-splits. Text and offsets have no second copy to drift.

Bounded ripple

The dirty range widens at each edge until the tokenizer calls the boundary stable. A word run is the limit, and the window is capped, so one edit never re-tokenizes the document.

Six reactors

BPE-A, BPE-B, WordPiece, a regex lexer, a constraint check and a stability check run over the same diff on sharded workers. No queue between them: a shard that cannot keep up re-lexes on its next idle moment and says so.

Anchored constraints

A span is planted by token, stored as a byte anchor, and shifted by every edit that lands before it. Rules can be retuned in place, keeping the span's identity and its warnings.

Stable warnings

Identity is kind, reactor and span bucket. A re-raise inside 250 ms bumps a flap count and sends nothing; absence starts a quiet clock; the feed settles instead of strobing.

A log, not a guess

Every batch is appended to an edit log and the rope is snapshotted on a revision and idle clock. A restart replays and re-tokenizes, so it can only land where the live path landed.

Run it

# server, page and socket
cargo run --release -p loom-srv        # http://127.0.0.1:8787/  (ws /ws)

# the gate: edit → diff over a real socket, window included
cargo run --release -p loom-cli -- bench

# the pipeline alone, no window: the floor under that number
cargo run --release -p loom-cli -- bench --core

# end to end: HTTP, snapshot, diff, warning, clear, resync, unplant
LOOM_PORT=8787 node web/smoke.mjs

# the page itself, driven in headless chromium over the DevTools protocol
node web/uitest.mjs --shot loom.png

# the edit-to-diff target, gated; what the window costs and buys
node web/window.mjs http://127.0.0.1:8787/

The page shows the rope, the diff lane, the warning feed, the reactor bank and the constraint sidebar. Clicking a constraint marks the chips its anchor covers; the rule buttons retune a marked span in place, and the × takes it back out.

What it is not

  • No model inference. The reactors are tokenizers and checks, not a network call.
  • No authentication, no accounts, no multi-tenant story.
  • No rich text: one document per server process, one byte stream.
  • No full-document re-tokenization per edit, and no JSON on the hot path.
