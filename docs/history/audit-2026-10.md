### Check architecture: per-host evals
**Status:** ✅ Completed (`f0230e9`)

The monolithic `host-eval-all` check passed ~20 host toplevels as env attrs of a single `runCommand` and kept getting OOM-killed (this machine reproduced it 3×). Replaced with 22 per-host `host-eval-<host>` derivations: each forces exactly one host's module-system eval by interpolating the toplevel into the echoed message and strips the context (`unsafeDiscardStringContext`), so the derivation is a trivial echo and CI/garnix can parallelise. Rejected designs: `deepSeq toplevel` (blows eval call depth) and `test -e ${toplevel}` in the builder (string context would build the host closure).

**Superseded 2026-10-15.** Splitting per host fixed CI (parallel runners) but not the local path, because those derivations lived in `checks.<system>` and `nix flake check`/`task checks:quick` force every attribute of that output in ONE process — the same 23 evaluations, now measured at 6078.5 MiB peak and SIGKILLed (exit 137), plus `flake check`'s own validation of `nixosConfigurations`. Toplevel forcing was also the costly half. Current design: `checks.<system>` forces no host at all (registry + attr names only), and the per-host gate moved to its own `hostChecks.<arch>.<host>` output, which forces the module system and every assertion (13.16 s / 720 MiB for frieren) but not the system derivation graph. See AGENTS.md § "never run `nix flake check` on a small host".

## Historical: Architecture (April 2026 — superseded)

> Task namespace names survive, but the nullclaw smoke checks and xs/OAuth helpers shown below no longer exist.

### Task Control Plane
Simplified namespace structure:
- `infra:*` - Host lifecycle, secrets, SOPS operations
- `agents:*` - Operator helpers, xs wrappers, OAuth management
- `checks:*` - Validation and smoke checks
- `dev:*` - Git workflows, flake updates, site deployment
- `services:*` - Legacy compatibility wrappers (deprecated)

### Deployment Workflow
Standard deployment uses `infra:*` tasks:
```bash
task infra:plan:host:<host>     # Build/evaluate
task infra:apply:host:<host>    # Apply configuration
task checks:nullclaw:smoke:<host>  # Validate
```

Or combined:

### 2026-10-19 — Graph queries, and the decision model's real accuracy

- `ops:ask Q=…` / `scripts/task/kg-ask.sh`: English question → intent → jq over
  `.#knowledgeGraph.file` (new 49 KB store artifact). Routing is **deterministic**;
  the model is recorded, not obeyed: measured on the in-repo engine, 6-way intent
  `choice` scored 2/8 right with equal-length options and 0.20–0.44 confidence
  otherwise, because `engine.py` is a hash-embedding heuristic, not mmBERT.
- `ops:context` is the trigger side: sentinel status + the graph context for the
  host. Advisory — the monitor detects, it never acts.
- `ops:bench:kg` settled the router question with labelled sets, because one was
  not honest: keyword 14/14 rule-shaped / 6/10 paraphrase / 4/9 naming no node,
  Jev 13/14 / 9/10 / 7/9 at ~330 ms, in-repo `systemone-decision` 5/14 / 1/10 /
  4/9. A single-sentence "keyword wins 14/14" would have been a rigged
  conclusion drawn from the set phrased in the rules' own vocabulary. On the
  last set the rules lose but DECLINE (UNKNOWN) where Jev answers wrong.
- Policy that replaced it: when no rule matches, `ops:ask` returns the **context
  bundle** of the node the question names (`route: bundle`, neighbours in
  `related`) — a superset, so it cannot mis-pick a relation, offline at 0 ms
  against Jev's ~330 ms. The paraphrase gain (6/10 → 10/10) is **partly
  circular**: four labels name only a node, and "a node-naming question means
  that node's context" is the policy being tested, so those matches confirm it
  against itself. `ops:bench:kg` prints the bundle count beside the score.
- The query surface is explicit and gated: six patterns
  (`ops:kg:host|skill|doc|tag|comention|stats`, `FORMAT=json` throughout) plus
  `checks:kg`, which fails on a renamed field or node type or a dropped anchor.
